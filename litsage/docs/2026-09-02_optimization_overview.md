# 2026-9-2 项目优化概述

## 1. 优化背景

今天的工作主要围绕“用户自带文献入库”展开。项目原本更偏向公开文献检索与导入，但实际使用中，用户可能会上传自己的 PDF、Word、Markdown 或未发表资料，并希望这些资料进入个人资料库或指定研究项目。

因此，本轮优化的核心目标是：让系统更适合真实科研资料管理场景，而不只是处理外部公开论文。

## 2. 上传资料能力优化

上传资料界面从单文件上传扩展为多文件上传，支持一次选择并提交多篇文献。

设计上保留了原有单文件上传接口，同时新增批量上传接口。这样既不破坏已有功能，也能支持更自然的批量导入流程。

批量上传采用“逐篇处理、允许部分成功”的策略。某一篇文献失败，不会影响其他文献入库；返回结果中会标明每个文件的成功、失败、重复或错误原因。

## 3. 项目绑定方式优化

原先上传资料时需要填写项目 UUID，这对用户并不友好。实际使用中，用户更自然地会填写或识别项目名称，例如“乳腺癌项目研究”。

本轮将上传资料和手动资料中的项目输入改为项目下拉选择。用户可以先创建项目，再在上传页面直接选择项目；如果不选择项目，则资料进入个人资料库。

这个调整降低了使用门槛，也避免了把项目名称误填到 UUID 字段导致接口报错。

## 4. 数据库迁移与表结构修复

用户资料入库需要扩展 `papers` 表，并新增 `paper_files`、`paper_chunks` 等表，用于记录文件信息、正文分块、解析状态、来源类型和权限信息。

本轮发现数据库处于“部分表已创建，但 Alembic 版本未同步”的状态。原因是早期使用了 `create_all` 创建表，而 `create_all` 不会给已有表补字段，也不会完整管理迁移版本。

因此对迁移脚本进行了兼容性优化，使它可以识别已有表、已有字段和已有索引，只补齐缺失结构。这样数据库可以从半初始化状态平滑升级到当前模型需要的结构。

后续建议：数据库结构变化优先通过 Alembic 迁移管理，减少直接依赖 `create_all`。

## 5. PDF 解析链路优化

原来的 PDF 解析主要依赖 PyMuPDF 原生文本抽取。这个方式对文本型 PDF 有效，但对扫描版、双栏排版、图片型摘要区、特殊语言标题等情况不够稳。

本轮引入了分层解析思路：

```text
PyMuPDF 原生解析
Tesseract OCR 兜底
多模态大模型识别 PDF 页面
```

OCR 适合处理扫描件和图片型文字，多模态模型更适合理解论文首页、摘要区、标题、作者、图表和复杂排版。

## 6. 多模态模型接入思路优化

最初多模态只作为“PDF 原生解析失败”时的兜底。但实际案例表明，即使原生解析出了大量文本，也可能无法正确识别摘要或标题。

因此本轮将多模态从“文本抽取兜底”升级为“元数据识别能力”：

```text
title
abstract
authors
keywords
language
confidence
```

也就是说，只要开启多模态能力，系统会将 PDF 前几页渲染成图片，并交给当前配置的大模型识别文献元数据。

当前多模态模型直接复用 `OPENAI_MODEL`。如果该模型本身支持图片输入，就不需要额外配置单独的视觉模型。

## 7. 摘要生成策略优化

用户上传资料与外部公开文献不同。外部公开文献没有摘要可以选择跳过，但用户自带资料往往可能没有标准摘要，或者摘要标题不是英文 `Abstract`。

本轮优化了用户资料的摘要处理优先级：

```text
用户手动填写 abstract
原文中识别 Abstract / 摘要 / Rezumat
多模态模型识别或概括 abstract
文本 LLM 基于正文生成 ingestion_abstract
正文开头摘录兜底
```

这样可以减少“PDF 原文有摘要，但系统判断没有摘要”的情况，同时避免因为一次 LLM 调用失败就拒绝入库。

## 8. OCR 与本地环境配置

本轮接入了 Tesseract OCR 的可选调用方式。OCR 默认不是强制能力，而是通过 `.env` 开关启用。

配置思路是：系统程序本体由用户本地安装，Python 项目通过 `pytesseract` 调用。这样不会把重型 OCR 环境强行绑定到项目启动流程里。

当前配置支持英文和简体中文：

```text
eng+chi_sim
```

后续如果需要处理更多语种，可以继续扩展 OCR 语言包。

## 9. 前端调试体验优化

批量上传失败时，前端会显示后端返回的完整结果。这样可以直接看到每篇文件失败在哪一步，例如摘要识别、数据库字段、embedding、Milvus 写入等。

这个改动让后续调试更透明，也更适合逐步完善导入链路。

同时，前端导航将单独的“文献搜索”入口与“外部检索导入”入口合并，统一收敛为“文献检索与导入”。这样用户不需要在两个相似功能之间来回判断，外部文献发现、候选筛选和入库操作集中在同一个工作流中。

候选文献筛选阶段也加入了项目绑定能力。用户可以在导入外部候选文献时搜索并选择已有项目，导入完成后自动把所选文献绑定到该项目；如果暂时不需要归入项目，也可以选择不绑定。

## 10. 测试与稳定性

本轮补充了若干测试，主要覆盖：

```text
批量上传 multipart 请求
空 project_id 处理
Abstract 摘要识别
Rezumat 摘要识别
多模态摘要优先级
LLM 失败后的摘录型摘要兜底
```

这些测试的目的不是追求覆盖所有 PDF 情况，而是保护今天新增的关键路径，避免后续改动把已修复的问题重新引入。

## 11. RAG 问答链路优化

RAG 系统从“基础向量召回 + 拼接回答”向“带范围控制和证据回填的问答链路”推进。

本轮重点补齐了三个方向：

```text
1. 问答接口接入 PostgreSQL 会话
2. 根据 paper / project / search_results 范围解析可访问文献
3. Milvus 命中 chunk 后回 PostgreSQL 查询标题、页码、原文和权限
```

这样 Milvus 继续承担向量召回职责，PostgreSQL 则负责权限、项目归属和可审计证据。回答中的 citation 不再只返回 `Unknown paper`，而是尽量回填真实标题、chunk_id 和页码位置。

这一步之后，RAG 仍不是最终形态，但已经从原型问答进入了更可信的项目级问答基础阶段。

后续可继续扩展：

```text
混合检索
重排序
上下文压缩
答案逐句引用
多轮会话记忆
更严格的权限过滤下推
```

## 12. 项目问答记录与项目总结

为了支持客户围绕同一个研究项目进行多次提问，本轮新增了项目问答记录能力。项目级 RAG 问答完成后，系统会保存问题、回答和引用来源，形成项目研究过程中的阶段性知识沉淀。

在项目服务中，原来的“项目批量总结”入口被替换为“项目总结”模块。用户不再需要手动填写项目 ID，而是通过搜索项目库和下拉框选择已有项目，然后生成阶段性总结。

项目总结会综合：

```text
项目内已绑定文献
项目文献摘要
历史项目问答记录
问答中引用的证据线索
```

这个改动让项目不只是一个资料容器，而开始具备“研究过程记录”和“阶段性归纳”的能力。

## 13. 总体优化思路

今天的优化方向可以概括为三点：

```text
从单篇上传走向批量资料入库
从手填 ID 走向面向用户的项目选择
从单一文本解析走向 OCR + 多模态 + LLM 的分层理解
从基础 RAG 原型走向项目范围内的可信证据问答
```

这使项目更接近一个“科研资料知识库 Agent”，而不只是一个论文搜索工具。它可以处理公开论文，也可以处理用户自己的未发表资料、内部报告和项目文档，为后续的项目级问答、综述生成、图表理解和研究助手能力打基础。
