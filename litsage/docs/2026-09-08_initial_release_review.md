# LitSage 初版开发总结文档

记录日期：2026-09-08

## 1. 项目定位

LitSage 初版定位为一个面向科研项目的文献智能搜索、资料入库、知识库问答与阶段性总结系统。

项目最初从“文献搜索与总结 Agent”的想法出发，开发过程中逐步扩展为一个以项目为中心的科研资料管理系统：用户可以检索 PubMed 等外部数据库文献，也可以上传自己的 PDF、Word、Markdown 或未发表资料；系统将文献和资料沉淀到 PostgreSQL 与向量库中，再围绕具体研究项目提供问答、总结、文献管理和历史问答管理能力。

当前版本更准确的描述是：

> LitSage 是一个具备 Agent 化扩展基础的科研文献知识库与 RAG 分析系统。

它已经具备文献检索、入库、解析、向量化、项目绑定、知识库问答、阶段性总结和 MCP 工具化接口，但还没有形成成熟 Agent 所需的任务规划、状态管理、多工具自动编排和自我校验闭环。

## 2. 初版已完成能力

### 2.1 后端基础服务

项目后端基于 FastAPI 构建，主要提供用户认证、项目管理、文献管理、资料上传、RAG 问答、阶段总结、文献删除等接口。

初版已经完成：

- 用户注册、登录和认证流程。
- PostgreSQL 数据持久化。
- Alembic 数据库迁移。
- 基础配置管理与 `.env` 环境变量加载。
- 文献、项目、问答、切片等核心表结构。
- 自动建表和迁移方案。

### 2.2 文献检索与导入

文献导入模块以 PubMed 为优先数据源，同时保留 arXiv、Semantic Scholar 等扩展入口。

初版实现了：

- 外部数据库文献检索。
- PubMed 文献元数据解析。
- DOI、PMID、PMCID 等标识信息保存。
- 候选文献预览。
- 用户选择候选文献后导入。
- 重复文献检测。
- 文献导入后可绑定到项目。
- 中文关键词通过大模型改写为英文检索词，提高 PubMed 检索命中率。

### 2.3 全文获取与解析

全文获取经历了多次调整。早期方案主要尝试通过 DOI 页面和 PDF URL 下载 PDF，后来发现出版商页面、PMC 跳转、防爬页面、验证码、HTML challenge 都会造成不稳定。

最终初版形成了更稳妥的优先级：

1. PubMed / PMC 文献优先尝试官方结构化全文。
2. 如果存在 PMC ID，优先尝试 BioC 或 OAI-PMH 等结构化接口。
3. 结构化全文不可用时，再尝试 PDF 下载。
4. PDF 下载失败时保留文献元数据，不强行入库错误全文。
5. 对 PDF 页面可渲染为图片，并预留多模态模型解析路径。

这个方案比单纯抓 PDF 更适合 PubMed 场景，也能减少验证码、跳转和 HTML 页面伪装 PDF 带来的失败。

### 2.4 用户自带资料入库

项目中加入了用户上传私有资料和未发表资料的设计。

初版支持：

- PDF、Word、Markdown 文件上传。
- 多文件批量上传。
- 上传资料默认 private。
- 资料可绑定项目，也可进入个人资料库。
- 用户可手动覆盖 title / abstract。
- PDF 原生文本解析。
- OCR 与多模态解析能力预留。
- 资料重复上传检测。

这个能力是项目的重要差异点，因为客户实际使用时不一定只研究已发表论文，还可能有内部资料、实验报告、会议材料、未发表初稿等。

### 2.5 向量化与 RAG

初版已经接入 embedding 与向量库能力，支持文献摘要、全文切片和项目知识库问答。

已实现：

- 摘要向量化。
- 全文切片入库。
- `paper_chunks` 同步保存在 PostgreSQL，便于调试、审计和后续重建向量库。
- Milvus 向量库支持。
- 项目范围内的文献检索。
- RAG 问答。
- 引用来源构建。
- 无效图像占位符和不可用片段过滤。

当前 RAG 能力已经可用，但还属于基础 RAG。它能根据项目文献片段回答问题，但还没有完整的检索质量评估、证据覆盖校验、答案自检和多轮任务状态。

### 2.6 项目管理与阶段总结

项目管理从简单的项目创建，扩展为围绕研究项目持续工作的管理入口。

初版实现：

- 创建项目。
- 查看项目已收录文献。
- 将文献绑定到项目。
- 从项目中批量移除文献。
- 查看项目历史问答。
- 删除无意义问答。
- 阶段性总结移动到研究问答模块下。
- 阶段性总结支持用户输入具体问题。
- 大模型判断问答是否适合作为阶段总结上下文。

这使项目不只是文献列表，而是能沉淀“客户围绕课题反复提问后的知识轨迹”。

### 2.7 Streamlit 前端

项目初期没有前端，后续使用 Streamlit 搭建了一个本地测试和演示界面。

当前前端主要用于：

- 用户注册和登录。
- 登录后隐藏左侧登录表单。
- 文献检索与导入。
- 用户资料上传。
- 项目管理。
- 项目文献绑定。
- 候选文献绑定项目。
- 知识库问答。
- 阶段性总结。
- 项目文献和问答管理。
- 文献删除。

Streamlit 前端保留的意义是：开发者和客户可以直观看到系统能力，而不是只通过 API 或 MCP 调用。

### 2.8 MCP 封装

项目初版最后加入了 MCP Server，使 LitSage 的能力可以被外部 Agent 或 MCP 客户端调用。

已完成：

- MCP Server 适配层。
- stdio 默认启动模式。
- SSE 网络访问模式。
- 外部 IP 调用测试脚本。
- MCP 客户端测试脚本。
- 工具函数封装。
- 运行时 LLM 配置层。
- MCP 工具强制传入调用方自己的 `llm_config`。
- 支持视觉模型参数 `vision_model`。
- 保留原 FastAPI 和 Streamlit 前端。

当前已封装 MCP 工具包括：

- `list_projects`
- `create_project`
- `list_project_papers`
- `list_project_qas`
- `bind_papers_to_project`
- `remove_project_papers`
- `delete_project_qas`
- `search_literature`
- `import_literature_candidates`
- `search_my_library`
- `ask_project_knowledge_base`
- `summarize_project_stage`
- `create_manual_material`
- `upload_user_material`
- `delete_paper`

MCP 封装让项目从单一 Web 应用开始向“可被外部智能体调用的科研知识库服务”转变。

## 3. 开发过程中遇到的问题与解决方案

### 3.1 数据库连接配置不一致

问题：

运行初始化脚本时，输出的数据库连接密码与 `.env` 或 `config.py` 中当前配置不一致，导致数据库连接失败。

原因：

配置来源不统一，可能存在旧环境变量、缓存配置、不同运行目录加载了不同 `.env` 文件等问题。

解决方案：

- 统一通过配置模块读取数据库连接。
- 检查脚本运行目录。
- 输出实际加载的连接字符串用于排查。
- 确认 `.env` 与运行环境一致。

经验：

后端项目必须确保 FastAPI、脚本、迁移工具读取同一套配置，否则数据库问题会非常隐蔽。

### 3.2 注册接口 500

问题：

FastAPI docs 中测试注册接口返回 `500 Internal Server Error`。

原因：

注册接口依赖数据库表结构、模型字段、认证逻辑和事务提交，任一环节异常都会表现为 500。早期主要集中在数据库表未创建或配置未对齐。

解决方案：

- 增加自动建表配置。
- 明确使用 Alembic 迁移。
- 检查数据库实际表结构。
- 通过测试脚本单独验证注册逻辑。

经验：

后端接口报 500 时，前端界面只能看到笼统错误，必须回到 uvicorn 控制台日志和数据库表结构层面排查。

### 3.3 前端注册成功但数据库看不到数据

问题：

Streamlit 前端提示注册成功，FastAPI 返回 `201 Created`，但用户在 DBeaver 中看不到数据库更新。

原因：

常见原因是前端调用的后端、后端连接的数据库、DBeaver 查看的是不同数据库实例或不同 schema。

解决方案：

- 检查后端实际 `DATABASE_URL`。
- 打印运行时数据库连接。
- 确认 DBeaver 连接同一个库和 schema。
- 避免多份 `.env` 或多个 PostgreSQL 实例混淆。

经验：

“接口成功但数据库没有数据”优先怀疑连接目标不一致，而不是业务代码没有 commit。

### 3.4 502 Bad Gateway

问题：

访问服务或测试 MCP SSE 时出现 `502 Bad Gateway`。

原因：

一类是后端服务没有启动或端口不对。另一类是在 MCP SSE 测试中，系统代理拦截了本机或内网请求，导致请求没有进入本地 uvicorn 服务。

解决方案：

- 检查服务是否启动。
- 检查端口是否监听。
- 使用 `curl --noproxy "*"` 验证。
- MCP 测试脚本默认关闭系统代理。

经验：

本机地址 `127.0.0.1` 仍可能被代理环境影响，尤其在 HTTP 客户端默认读取系统代理时。

### 3.5 PubMed PDF 下载不稳定

问题：

PubMed 检索到文献后，有时只能拿到摘要，PDF 下载失败，或拿到 HTML 页面而不是 PDF。

原因：

- PubMed 页面不一定直接给 PDF。
- DOI 会跳转到出版商页面。
- 出版商页面可能有验证码或 JavaScript challenge。
- PMC `/pdf/` 链接可能会重定向到真实 PDF 文件名。
- 普通 HTTP 请求与浏览器访问结果不完全一致。

解决方案：

- 下载请求增加 Chrome 浏览器请求头。
- 检测响应是否真的是 PDF。
- 记录 final URL。
- 遇到 HTML challenge 时标记需要人工处理。
- 对 PMC 文献优先使用官方结构化全文接口，减少对 PDF 抓取的依赖。

经验：

科研文献全文获取不能只靠拼 URL 和下载 PDF，必须区分 PubMed、PMC、DOI、出版商页面几种路径。

### 3.6 PMC 链接跳转问题

问题：

数据库中的 PMC PDF URL 访问时会跳转到真实 PDF 文件，但程序拿到的 final URL 有时仍是目录 URL。

原因：

不同域名、重定向策略、请求头和客户端行为会导致程序与浏览器表现不同。

解决方案：

- 专门增加 PMC 解析策略。
- 优先从 PMC 官方开放接口获取全文。
- 对 PDF URL 记录 requested URL 和 final URL。
- 避免用不够具体的 `/pdf/` 目录链接覆盖真实 PDF 文件链接。

经验：

PMC 是 PubMed 全文获取中最重要也最值得单独优化的数据源。

### 3.7 多模态 PDF 解析失败

问题：

PDF 渲染成 PNG 后传给大模型，模型返回“无法识别图片”或类似道歉文本。

原因：

可能原因包括模型接口不支持当前传参格式、服务商视觉模型与文本模型不一致、base64 图片格式问题、图片质量问题、或 API 返回了 reasoning 文本而不是最终输出。

解决方案：

- 增加 `DEEPSEEK_VISION_MODEL`。
- 支持单独配置视觉模型。
- 增加多模态输出校验，过滤“无法识别图片”等无效结果。
- debug 脚本输出 PDF 下载、渲染图片、原生文本、多模态结果。
- 对 PubMed / PMC 优先采用结构化全文，减少多模态依赖。

经验：

多模态是重要能力，但不能作为唯一可靠入口。结构化全文、PDF 原生文本、OCR、多模态应该按场景组合使用。

### 3.8 RAG 回答只看到标题或无效片段

问题：

用户对项目提问时，回答显示只能看到标题，或只看到 `[Unsupported Image]`。

原因：

文献入库时没有成功提取正文，向量库中可能只有摘要、标题，甚至错误地写入了图片识别失败的文本。

解决方案：

- 过滤不可用片段。
- 避免把模型道歉文本当正文入库。
- PubMed / PMC 优先结构化全文。
- 增强调试脚本检查每篇文献实际写入了哪些 chunk。

经验：

RAG 回答质量不是由大模型单独决定的，核心在于入库文本是否真实、完整、可检索。

### 3.9 阶段性总结 500

问题：

阶段性总结模块调整后出现 `500 Internal Server Error`。

原因：

新增字段和数据库实际结构不同步，迁移未执行或旧数据库缺少新列。

解决方案：

- 增加 Alembic 迁移。
- 增加兼容 fallback。
- 提醒执行 `alembic upgrade head`。

经验：

只要模型字段变更，就必须同步数据库迁移；前端功能报错时，也要优先检查后端 schema 与数据库表是否一致。

### 3.10 MCP 版本兼容问题

问题：

运行 `python -m app.mcp.server` 报错：

```text
No module named 'mcp.server.fastmcp'
```

原因：

安装了 `mcp 2.x`，但项目使用的是 `mcp 1.x` 的 `FastMCP` API。

解决方案：

- 将依赖固定为 `mcp[cli]>=1.27,<2`。
- 将本地环境降级到 `mcp 1.30.0`。
- 增加 MCP server import 测试。

经验：

新兴 SDK 变化很快，必须固定主版本，否则今天能跑的代码明天可能直接导入失败。

### 3.11 MCP SSE 暴露安全风险

问题：

SSE 模式可以让外部 IP 访问 MCP 服务，但也可能暴露本机服务能力。

风险：

- 未授权用户可能调用项目、文献和删除工具。
- 错误信息可能泄露本机路径。
- 数据库和文件上传能力可能被滥用。

当前处理：

- 默认 MCP 使用 stdio，只本机客户端可拉起。
- SSE 需要显式启动。
- 删除文献工具需要 `confirm=true`。
- 文档中提示不要公网裸露服务。

后续建议：

- 增加 `MCP_API_TOKEN`。
- token 绑定用户 ID。
- 工具按 read / write / delete 权限分级。
- 增加调用日志和审计记录。

## 4. 项目核心优势

### 4.1 面向真实科研项目，而不是一次性问答

项目不是单纯让用户上传一篇论文然后总结，而是围绕“研究项目”组织文献、资料、问答和阶段总结。

这更符合科研客户的实际工作方式：一个课题会持续积累资料、反复提问、阶段性整理思路。

### 4.2 支持私有资料和未发表资料

相比只检索公开论文的工具，LitSage 支持用户上传自己的 PDF、Word、Markdown 和未发表资料。

这让系统可以服务于：

- 内部研究报告。
- 未发表论文。
- 实验记录。
- 会议材料。
- 客户自己的知识资产。

这是项目后续商业化或客户交付时的重要差异点。

### 4.3 PubMed 优先，贴近医学科研场景

开发过程中明确了 PubMed / PMC 是医学文献场景的核心数据源，并针对 PubMed 元数据、PMCID、PMC 结构化全文做了单独优化。

这比泛泛地接入多个搜索源更有价值。

### 4.4 前端、API、MCP 三种访问方式并存

初版保留了：

- FastAPI 后端接口。
- Streamlit 本地前端。
- MCP 工具调用接口。

这让项目既能人工操作，也能被外部 Agent 调用，具备进一步平台化的基础。

### 4.5 有较清晰的扩展方向

当前代码已经按 services 拆分业务模块，后续可以继续扩展：

- 异步任务。
- Agent 编排。
- 鉴权。
- 多租户。
- 更强 RAG。
- 更完整的文献分析报告。

## 5. 项目核心劣势

### 5.1 还不是成熟 Agent

当前系统主要是 RAG 应用和工具服务集合，大模型调用多为单次调用，没有完整的任务规划、状态管理、自动重试、自我校验和多工具推理闭环。

因此目前更适合称为 Agent-ready，而不是成熟 Agent。

### 5.2 全文获取仍存在外部不确定性

PubMed、PMC、DOI、出版商页面、验证码、跳转、防爬策略都会影响全文获取。

虽然已经增加结构化全文优先策略，但仍无法保证所有文献都能自动获取全文。

### 5.3 多模态解析稳定性仍需加强

多模态大模型能力很强，但 API 调用格式、图片传输、模型选择、输出解析都可能造成失败。

后续需要进一步建立：

- 多模型 fallback。
- OCR 与多模态融合。
- 页面级解析状态。
- 表格和图像单独结构化提取。

### 5.4 RAG 质量依赖入库质量

如果导入阶段只获得标题、摘要或无效文本，RAG 回答就会明显变差。

当前还缺少完整的入库质量评分，例如：

- 全文覆盖率。
- chunk 数量。
- 摘要质量。
- OCR 成功率。
- 图表解析状态。

### 5.5 安全和权限还处于初级阶段

MCP SSE 对外开放前必须增加鉴权。当前系统虽然有用户 ID 过滤，但 MCP 工具仍需要更严格的 token 到 user_id 映射，避免外部调用者伪造 user_id。

### 5.6 缺少生产级任务队列

文献导入、PDF 下载、多模态解析、embedding、向量入库都可能耗时较长。当前第一版偏同步流程，后续需要 Celery 或其他任务队列来管理长任务。

## 6. 项目未来展望

### 6.1 升级为真正的科研 Agent

后续可以增加 Agent Run 层，让系统从“用户点接口”升级为“用户提出研究目标，系统自动拆解任务”。

推荐新增：

- `agent_runs` 表。
- `agent_steps` 表。
- 工具调用日志。
- 任务状态机。
- 失败重试和恢复机制。
- 阶段性计划生成。
- 结果自检。

典型目标：

> 用户输入“帮我分析肝癌免疫治疗近三年的研究进展”，系统自动检索 PubMed、筛选高相关论文、获取全文、入库、生成综述框架、指出研究空白。

### 6.2 建立 LLM 调用管理层

当前 LLM 调用还比较直接。未来应建立统一的模型调用层：

- retry / backoff。
- 超时控制。
- fallback 模型。
- 文本模型与视觉模型分流。
- token 统计。
- cost 统计。
- 调用日志。
- 输出格式校验。

这样系统会更稳定，也更容易定位问题。

### 6.3 增强文献解析质量

未来文献解析可以从“提取文本”升级为“结构化理解文献”。

建议增加：

- 标题、摘要、关键词、方法、结果、结论结构化提取。
- 图表题注提取。
- 表格结构化。
- 研究设计类型识别。
- 样本量、疾病类型、实验方法、数据集、指标抽取。
- 证据等级评估。

这会让项目从 RAG 问答进入“科研信息抽取与分析”阶段。

### 6.4 强化项目阶段总结

阶段性总结后续可以更像课题管理工具：

- 自动整理研究假设。
- 自动生成研究路线图。
- 汇总已读文献观点。
- 标记冲突结论。
- 生成下一步实验建议。
- 追踪客户反复关注的问题。
- 输出阶段报告。

### 6.5 MCP 安全化和产品化

如果要给外部用户调用 MCP，需要继续做：

- MCP token 鉴权。
- token 绑定 user_id。
- read / write / delete 权限。
- 请求审计日志。
- 限流。
- 文件大小限制。
- 外部用户自带 LLM 配置。
- 反向代理和 HTTPS。

这样 LitSage 才能安全地作为外部 Agent 的科研工具服务。

### 6.6 前端从 Streamlit 走向正式产品界面

Streamlit 适合初期测试和演示，但如果项目继续发展，建议后续迁移到正式前端：

- React / Vue / Next.js。
- 更完整的项目仪表盘。
- 文献筛选工作台。
- 文献详情页。
- 图表解析结果页。
- 问答历史管理。
- 阶段报告编辑器。

## 7. 当前阶段结论

LitSage 初版已经完成了从想法到可运行系统的关键闭环：

1. 用户可以创建账号和项目。
2. 用户可以检索和导入文献。
3. 用户可以上传自己的私有资料。
4. 文献可以绑定项目。
5. 系统可以基于项目知识库问答。
6. 项目问答可以沉淀为阶段总结上下文。
7. 文献和问答可以管理和删除。
8. 项目能力可以通过 MCP 暴露给外部 Agent。

当前版本的价值在于，它已经不只是一个简单的大模型包装页面，而是开始形成了“科研项目知识库”的底座。

但从 Agent 标准看，它仍是初级阶段。未来真正的增长点不在于“调用大模型总结文献”，而在于把文献检索、资料解析、证据抽取、项目记忆、任务规划和阶段性研究建议串成一个长期运行的科研助手。

初版到这里可以作为一个阶段性结束点。后续如果继续推进，最优先的方向应是：

1. MCP 鉴权。
2. Agent Run 状态管理。
3. LLM 调用重试与日志。
4. 文献解析质量评分。
5. RAG 回答证据校验。
